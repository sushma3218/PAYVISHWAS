# PAYVISHWAS AI Architecture

This document describes the hybrid Artificial Intelligence architecture used in PAYVISHWAS, adhering strictly to the **Right Intelligence for the Right Task** principle and fulfilling the requirements for the **Razorpay Buildathon Track 02 (AI Risk Manager)**.

## Hybrid Approach

PAYVISHWAS uses a mix of deterministic logic, statistical/ML models, and Large Language Models (LLMs). LLMs are *never* used to directly authorize financial actions or bypass security policies.

### 1. Deterministic Logic (The Guardrails)
- **Use Case**: Authorization, state machine transitions, idempotency checks, financial limits, and core policy enforcement.
- **Why**: Zero hallucinations allowed. Financial safety must be mathematically guaranteed.

### 2. Statistical/ML Logic (The Track 02 Evaluated Core)
- **Use Case**: Risk prediction, anomaly detection, transaction velocity scoring, probability estimation.
- **Why**: We need measurable, reproducible, and back-testable numbers (Precision, Recall, F1) for financial risk evaluation.
- **Implementation**: The **Risk Detection Model** is implemented as an ML classification system that scores the probability of **Fraud/Chargeback Loss** on a given transaction.

### 3. LLM Reasoning (The Brains)
- **Use Case**: Contextual reasoning, root-cause explanation (parsing complex gateway errors), strategy generation, and human-readable decision explanation.
- **Why**: LLMs excel at unstructured data parsing, synthesis, and explanation, which is perfect for generating human-readable alerts and strategies.

## The ML Risk Model (Track 02 Core)

The core requirement of Track 02 is a measurable risk prediction model for a specific loss class.

**Primary Loss Class**: Fraud/Chargeback Risk on High-Value and High-Velocity Transactions.

### Model Pipeline

1. **Input Features**:
   - Transaction Amount (Numerical)
   - Transaction Velocity (Categorical/Numerical - e.g., transactions per hour)
   - Retry Count (Numerical)
   - Failure Type (Categorical)
   - Customer History (Numerical - previous successful vs. failed)
   - Payment Method (Categorical)
   - Bank/System Health Signals (Numerical)

2. **Output Target**:
   - `risk_score` (0.0 to 1.0)
   - `risk_level` (LOW, MEDIUM, HIGH, CRITICAL)
   - `predicted_outcome` (SAFE, POTENTIAL_LOSS)
   - `confidence` (0.0 to 1.0)

3. **Evaluation (Held-Out Test Set)**:
   The system includes a dedicated `Risk Evaluation Center` in the dashboard that displays metrics generated by running the model against a held-out test set (e.g., 1,500 samples not seen during training).
   - **Metrics Tracked**: Precision, Recall, F1 Score, Confusion Matrix.
   - **Financial Cost Matrix**: Evaluates the cost of False Positives (lost conversions/friction) vs. False Negatives (actual financial loss/fraud).

## Agent Orchestration

PAYVISHWAS uses a decentralized swarm orchestrator. 

### Model Abstraction Layer
The application interacts with LLMs through an abstraction interface to ensure vendor independence (e.g., Anthropic, OpenAI):

```python
class AIProvider(ABC):
    @abstractmethod
    def analyze(self, data: dict) -> dict: pass
    
    @abstractmethod
    def reason(self, context: str) -> str: pass
    
    @abstractmethod
    def generate(self, prompt: str) -> str: pass
    
    @abstractmethod
    def explain(self, decision_data: dict) -> str: pass
```

### Proactive Payment Health
Beyond reactive recovery, a background job uses statistical ML to monitor live payment stream health (e.g., moving average of UPI failure rates). If an anomaly is detected (e.g., a 300% spike in timeouts for Bank X), it generates a **Proactive Alert**.
